# 验收与交付

## 四道检查

1. **内容与来源**：对应原口播；口播点名的实体在画面上出现；素材许可已记入 assets.json；数字有依据；截图展示的正是所说的功能；再现与示意已标注；标为原始或修改前的画面确实是原素材，全局处理没有越过声明的范围；生成内容只含已授权的人物、品牌与信息。动态段落有选择依据，定制 MG 有具体的表达缺口。
2. **单镜头**：实际解码，核对帧率、画幅、长度；关键帧覆盖入场、峰值、落定；中文字形、换行、安全区、遮挡、透明边缘、末帧都正常。对照 Shotcraft 时读取准确实现、看动态效果。
3. **时间与声音**：`plan_tools check --ready` 通过；有 anchor 的镜头已用当前剪辑 `cue.py sync` 过，且无前缀匹配 warning；目标时刻误差检查到帧；口播没有剪断、重复或缺失，剪点与疑点的试听合集已听过或已交用户确认（见下方声音证据）；字幕对应剪后时间；SFX 进入最终混音；BGM 让位于人声；最终响度与峰值实测。
4. **整片**：从实际渲染抽查每个切点前后、开头、中段、结尾，再完整连看连听。核对信息递进、动静交替、全貌与细节、人物回归、语义落点、阅读停留、转场依据；强动作之间有间隔，相同镜头的重复有理由。音频/文案模式画面全覆盖；人物模式不遮脸；全片只有一套字幕。

四道检查完成后才标 `verified`（核心原则 5）。

## 声音证据

- ASR 文字对上、响度合规、帧数一致，分别只证明文字、电平和长度，不证明听起来自然。听感只能靠实际听审。
- 不能实际听审时，开始剪辑就说明这一点，不要等用户反复指出问题后才说。交付 `voice_edit.py listen` 的试听合集与清单，状态写"待试听确认"。
- 汇报措辞跟证据走：听过才写"已修顺""无卡顿"；没听过就写做了什么，例如"删去 2 处词中停顿，待试听确认"。工程记录与对用户的说法用同一标准。
- 只改声音、版式不变时，旧的视觉验收可以沿用；声音、字幕对齐和最终导出文件要重新核验。最终文件要再截一次试听，不能只检验中间音轨。

## 自检打分

整片（或长片的一章）渲染完成后，出抽帧拼图和手机尺寸拼图（单格约 360 像素宽），用挑错的眼光逐项打 1–10 分：

| 项 | 看什么 |
|---|---|
| 开场 | 前 2 秒是否建立了关注对象，并与定位一致 |
| 手机可读 | 缩到 360 像素宽时，文字与关键数字是否清楚 |
| 动作质量 | 有无机械匀速、动作互抢焦点、无意义的停顿 |
| 节奏匹配 | 画面变化与旁白信息密度是否匹配，停留够不够读 |
| 构图 | 主体够大，没有大片空白或拥挤；人脸与字幕区不被遮挡 |
| 风格一致 | 色板、字体、弹簧档位统一；避开清单逐条通过；有参考片的风格按其标志特征逐条核对；无 PPT 感（见 [解说语法](explainer-grammar.md#5-去掉-ppt-感)） |
| 贴合原材料 | 事实、品牌、指定镜头与动作和确认方案一致 |
| 声画同步 | 关键动作贴近语义词或拍点，音效落在动作帧上 |

每个分数附上依据的时间点或拼图格号，说不出依据的分数不算；不用总分掩盖单项的低分。

列出最严重的 3 个问题及时间点，只重渲有问题的片段，再出新拼图、新分数，目标是每项 8 分以上。自检修复最多连续 3 轮；仍未达标时，报告具体镜头、证据与可选处理。每轮分数与问题记在 `verify/review_log.md`。

快速动作附近的问题在抽帧里容易漏掉，可把那一段连续 12 帧拼成一条来看：

```text
ffmpeg -ss <秒> -i <成片> -vf "scale=320:-1,tile=12x1" -frames:v 1 verify/strip.png
```

## 镜头意图核对

- 对照 [制作定位](production-profile.md)：受众与目的、内容、风格、时长是否落实到开场结尾、证据密度、字幕构图、动静与声音。章节长片查章节衔接、完整演示与持续阅读；综艺包装查原话与点评的区分、反应的真实性。每个输出版本分别核对尺寸、语言、时长与已核验的平台规格。
- 对照选择记录逐个 shot_id 检查：选定的卡、变体、风格、引擎与手法卡确实进入成片，指定动作原样呈现。交付后在用到的手法卡里追加使用记录。
- 对照准确 demo 与看过的动态参考，检查关键时值、遮罩、路径、落定；没看过样片的镜头单独标"无法对照验证"。
- 配方适配、配方加原创图解、纯定制 MG、保留原片，分别如实记录。
- 创意与参考的匹配靠导演判断（plan_tools 不验证这部分）。已确认的旧项目，在用户下次要求新制作或改版时才应用新流程。

## 独立审查

**局部修改**（只改文字、颜色等，时序与创意不变）：复用仍然适用的定位、参考与旧验收证据；检查改动帧、受影响的布局、接缝，以及新文件的解码、时长与声音；记录新版哈希与证据适用范围。改动扩散、结构或时间线变化、新增多个动画时，扩大验收范围。

**独立终检**：制作涉及多个动画或 Shotcraft 成片交付，且有可用的独立 Agent 时，提供最新成片、旁白/原文、已确认简报、镜头候选与 MG 决策、风格与避开清单、节奏说明、主计划、素材来源、卡片代码与参考样片，请其独立审查；问题附帧号或截图及影响。提交材料保持中性，不预设结论。

没有独立审查能力时，记录"未做独立审查"，完成自检后交付待审预览。只讨论方案、修改 Skill 或交接提示词时，不触发成片终检。

## 故障与续作

- 每次修改只重做受影响的镜头，最后整片重新合成并检查接缝。受影响范围以 `plan_tools.py diff` 的清单为准：`rerender` 重渲后 `stamp`，`reuse_moved` 复查接缝，`unverified` 确认或重渲。
- 外部生成按 production.md 的次数与预算上限执行。
- `project.md` 记录：已确认策略、当前 revision、主风格与避开清单、已完成与等待中的镜头、实际工具版本、下一步、阻塞项。中断后先核对这些记录与文件，复用未变的转录。
- 用户反馈先归到层级（设计语言、画面语义、声音），再在全片查同类问题；新约束、作用范围与例外记进 `project.md`。
- 同一处被再次指出时，先怀疑上一轮的诊断和验证方法：回到原素材，与上一版对比，写清上次改了什么、为何仍残留、这次换什么做法、怎么验证。先修最小片段并验证，再同步全片。声音问题按 [卡壳诊断](production.md#卡壳诊断) 处理。
- 外部回传的文件先核对 shot_id、版本、长度、画幅、声音与内容，匹配当前 revision 后再装入时间线。

## 交付层级

- **方案**：简报、剪辑策略、画面与风格方案，注明尚未制作。
- **外部制作包**：提示词、参考文件、任务编号、回收要求，注明等待生成。
- **预览**：可播放的完整低成本成片，列出未通过的检查与待确认点（包括未完成的听审）。
- **正式交付**：验证后的成片、项目工程与时间线、素材来源、验收记录与自检分数；有 BGM 且用户需要后期配乐时，另交一版无 BGM 但保留 SFX 的成片。

### 交付规格门禁（硬性）

- 正式交付前，对每个要交的成片文件跑一次，并把报告写进 `verify/`：

  ```text
  python <skill>/scripts/media_tools.py deliver-check <成片> --source <原素材> --report verify/deliver_check.json
  ```

  交付规格默认等于原素材的尺寸（竖屏口播通常 1080×1920 起）；用户另定规格或多来源时用 `--spec 1080x1920` 指定。报告列出分辨率、帧率、码率、时长、`color_transfer` 与声道。
- 非零退出即不得交付：成片短边或长边低于规格、横竖方向变了、文件名带草稿/预览字样、没有音轨。先查是哪一步降了尺寸（草稿渲染、合成画布、导出参数），修好重渲再跑，不要改规格去迁就成片。
- 警告逐条在验收记录里写明处理结果：HDR 原片（PQ/HLG）的成片仍带 HDR 传输特性，要做色调映射到 BT.709，除非已约定交 HDR；帧率、声道比原片少；码率低到草稿级；成片比原片短时确认是剪辑所致而不是渲染截断。
- 草稿与预览渲染只用于自查和给用户看方向，输出文件名必须带"草稿"或"预览"字样（如 `成片_草稿.mp4`），不得作为成片交付或改名后交付。例如 Video Use `render.py --draft` 为 720p CRF 28，只用于核对剪点；`--preview` 为 1080p CRF 22，用于质检；HyperFrames 参考片用 `PREVIEW_END` 截短，见 [制作路线](production.md#hyperframes)。
- 交给用户时写明成片的分辨率、帧率、码率、时长与文件大小，与 `deliver_check.json` 一致。

交给用户看的东西（风格方向、代表帧、样片、试听合集）给出能直接打开的文件路径，能在对话里展示的就直接展示。生成完毕不等于用户已经看到：用户说没看到时，先解决展示与访问，再请用户选择。

用用户看得懂的话说明结果与限制。发布、上传作品展示页或导出到外部服务，由用户提出后再做。剪映工程等导出能力单独核对并实测后再交付。
